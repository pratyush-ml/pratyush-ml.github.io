Introduction

This post is about how agents work. The idea came from a blog post I was reading from Tidy Design Principles — the motivation is straightforward: cover everything you need to know to build an agent, from first principles. To keep the scope manageable, I will not touch upon how inference itself happens. That is a topic for another day.

Before we can talk about agents, we need to understand what they are built on top of: LLMs. So we will trace the evolution of LLMs — from a simple Q&A bot all the way to systems with agentic capabilities — and layer in the other concepts (tools, harnesses, caching) along the way.

Here is the roadmap:

  1. LLMs as a Q&A bot — the stateless HTTP foundation
  2. Multi-turn conversations — how context is maintained
  3. System prompts — who sets the model’s behaviour
  4. Client-side control — forking, structured output, and why you are in charge
  5. Caching — why it is expensive
  6. Tool calls — giving the LLM access to functions
  7. The harness — who actually executes those tools
  8. What is an agent? — tying it all together

The Q&A bot is the foundation everything else builds on, so we will spend the most time there.

LLMs as a Q&A Bot

When the first GPT 3.5 came out, the interaction was beautifully simple: you ask a question, you get an answer. But to understand why agents are interesting, we need to understand the mechanics of that interaction at the protocol level — specifically, how it works over HTTP.

The HTTP foundation: statelessness

The first principle to grasp is that HTTP is stateless. Every request from the client to the server is a fresh, self-contained transaction. Once the server responds, it forgets everything about you.

This has a profound implication for LLM APIs: one question can only be answered in the context of a single request. The moment that transaction completes, the server retains no memory of your prior Q&A. The next time you send a message, the server starts from scratch.

Modern LLM platforms now have session and state management layers on top, but we are not concerned with those here. We care about the core capability of the LLM API itself, and that core is stateless.

This single fact — statelessness — is the thread that explains almost every “advanced” concept that follows.

This is a trimmed version of how the API works. There is a lot that goes on and is beyond the scope of the blog.

Multi-Turn Conversations

If the server forgets everything after each response, how do you have a conversation?

The answer: the client is responsible for maintaining context. You, the client, send the entire conversation history with every new request.

Here is how it works, step by step:

  1. Turn 1: You send your first message. The server responds. Transaction over — the server forgets.
  2. Turn 2: You want to ask a follow-up. So you send both the previous user message and the previous server response (now called the assistant message), followed by your new user message. The server reads the full history and continues the conversation.

This back-and-forth — one user message paired with one assistant response — is called a turn. A conversation is a sequence of turns, and the entire sequence is resent with every request.

All of this is transmitted as JSON. The messages array in the request body contains the ordered list of {role, content} pairs. That is the entire mechanism: a growing JSON list of messages, resent each time, because the server has no memory of its own.

System Prompts

Before a single user message is sent, there is one more role to understand: the system prompt.

There are two layers here:

  1. The model provider’s system prompt. Closed-source models like Claude ship with their own internal system prompt that defines baseline behaviour, safety guidelines, and operating principles. (You can find examples of these on Anthropic’s GitHub.) Open-source models, by contrast, give you full control — there is no hidden provider prompt.

  2. Your system message. On top of the provider’s prompt, you define a system message that sets the persona, tone, and constraints for your specific use case. Think of the provider’s prompt as the constitution and your system message as the local bylaws.

So a complete message list looks like:

[system]    You are a concise assistant that speaks in bullet points.
[user]      What is the capital of France?
[assistant] Paris.
[user]      And its population?
[assistant] ...

The system message sits at the top of the list. Because the entire list is resent on every turn, the system message is effectively persistent — not because the server remembers it, but because you include it every time.

Client-Side Control: You Are in Charge

Here is a consequence of statelessness that is easy to miss: because the client controls the message list, the client controls everything.

The server never decides what context to keep or discard — you do. This unlocks several powerful patterns:

Forking

At any point in a multi-turn conversation, you can fork: take the current message list, branch off, and start a parallel conversation from that point. You can run multiple branches simultaneously and pick the one that produced the best results. You can even jump back to an earlier turn and continue from there, ignoring later messages.

The LLM has no say in this. It simply processes whatever list you hand it.

Structured output

You can ask the LLM to return its answer in a specific format — say, a JSON object with particular fields. This does not change the underlying mechanism. The response is still JSON, still part of the same message list, still resent on the next turn. Structured output is just a cleaner contract on top of the existing JSON interaction.

The takeaway

What you send to the LLM at any given point — the system message, the assistant messages, the user messages, which turns to include or skip — is entirely controlled by the client. This is not a limitation; it is a superpower.

Caching

LLM providers offer prompt caching (also called KV cache reuse): the ability to store the computed representation of a message prefix on the server side so that subsequent requests with the same prefix do not have to reprocess it from scratch. You still send the full context every turn — you simply pay less for the cached portion (often around 10% of the normal input cost).

Why is caching expensive to offer? These inference servers run in a distributed fashion across GPU machines. Maintaining state across a distributed fleet of GPU nodes — keeping KV caches resident in memory, routing subsequent requests to the same node, managing eviction — is computationally and financially costly. The server was architected to be stateless, so any persistent caching layer is an optimisation bolted on top, and providers charge accordingly.

For most use cases, you can get by without caching. It becomes important at scale, when you are re-sending large context windows on every turn.

Tool Calls

Everything so far has been pure Q&A: the LLM generates text, you consume it. The next evolutionary step is tool calls.

Consider a simple question: “Is today my anniversary?”

To answer this, the LLM needs two pieces of information:

  1. Your anniversary date — a static fact. You can include this in the system prompt or user message. No tool needed.
  2. Today’s date — dynamic information the model weights themselves do not have. The model has no built-in clock. (Some providers, like OpenAI, inject the current date into the system context for their consumer-facing products, but the raw API does not guarantee this.)

This is where tool calls come in. You define a function — say, get_today_date() in Python — and describe it to the LLM. When the LLM recognises it needs the current date, it selects that tool and signals that it wants it called. This act — the LLM choosing from a set of available tools — is called a tool call.

The critical thing to understand: the LLM does not execute the tool. It merely says, “I want to use tool X with these arguments.” The actual execution is someone else’s job.

Newer models are better at deciding when to use a tool, but the tools themselves must always be explicitly defined. Tool calls are here to stay — they are the bridge between the LLM’s text world and the real world of computation.

The Harness

So the LLM says, “Call tool X.” Who actually runs it?

You do. The execution layer that sits between the LLM’s tool-call request and the actual function invocation is called the harness.

The harness is the glue that makes tool calls real. Here is the full cycle:

  1. The user asks a question.
  2. The LLM receives the message (along with the list of available tools).
  3. The LLM decides it needs a tool and returns a tool-call request (tool name + arguments).
  4. The harness intercepts that request, executes the actual function, and collects the result.
  5. The harness feeds the result back to the LLM as a new message.
  6. The LLM digests the tool output and produces its final answer.

What the harness actually does

The description above makes the harness sound like a simple pass-through. In practice, the harness is doing a surprising amount of work at each step:

Argument validation. The LLM might return arguments that are malformed, missing required fields, or of the wrong type. The harness validates the tool-call request before executing anything. If the LLM calls get_today_date(format="dd-mm-yyyy") but your function does not accept a format parameter, the harness catches that and returns an error message to the LLM — not a crash.

Execution. The harness calls the actual function. This could be a local Python function, an HTTP call to an external API, a database query, or a shell command. The harness is agnostic to what the tool does — it just needs to run it and capture the return value.

Error handling. What happens if the function raises an exception? If the external API is down? If the database times out? The harness must catch these failures, format them as readable error messages, and feed them back to the LLM. The LLM can then decide to retry, try a different tool, or tell the user that something went wrong. Without the harness handling errors gracefully, a single API timeout would kill the entire conversation.

Serialisation. The function might return a Python object, a pandas DataFrame, a list of dicts, or raw bytes. The harness must serialise that into a string (or a JSON string) that the LLM can read. If the result is too large — say, a database query returning 10,000 rows — the harness must truncate, summarise, or paginate it. The LLM cannot digest raw binary or arbitrarily large payloads.

Logging and observability. In production, you want to know which tools were called, with what arguments, how long they took, and what they returned. The harness is the natural place to log all of this. This is not optional — when an agent misbehaves, the harness logs are how you debug it.

Security and permissions. The harness is the enforcement point. If a tool can delete files or make payments, the harness is where you add confirmation prompts, rate limits, or permission checks. The LLM should never have direct access to destructive operations — the harness mediates everything.

A concrete harness implementation

Here is what a minimal harness looks like in Python:

import json

def get_today_date():
    from datetime import date
    return date.today().isoformat()  # e.g., "2026-06-27"

def check_bank_balance():
    # In reality, this would call your bank's API
    return {"balance": 54000, "currency": "INR"}

# Registry: maps tool names to actual functions
TOOLS = {
    "get_today_date": get_today_date,
    "check_bank_balance": check_bank_balance,
}

def run_harness(tool_call):
    """Execute a single tool-call request from the LLM."""
    name = tool_call["name"]
    args = tool_call.get("arguments", {})

    # 1. Validate: does this tool exist?
    if name not in TOOLS:
        return json.dumps({"error": f"Unknown tool: {name}"})

    func = TOOLS[name]

    # 2. Execute with error handling
    try:
        result = func(**args)
    except TypeError as e:
        # Argument mismatch
        return json.dumps({"error": f"Invalid arguments: {e}"})
    except Exception as e:
        # Any other failure
        return json.dumps({"error": f"Tool execution failed: {e}"})

    # 3. Serialise
    if isinstance(result, str):
        return result
    return json.dumps(result)

And here is how the harness is called in the loop:

# The LLM returned a tool-call request
tool_call = {"name": "get_today_date", "arguments": {}}

# The harness executes it
tool_result = run_harness(tool_call)  # returns "2026-06-27"

# The harness result is appended to the message list
messages.append({
    "role": "tool",
    "name": "get_today_date",
    "content": tool_result
})

# The updated message list is sent back to the LLM

The harness is your code. You write it. It is the cycle of “LLM says do X → you validate X → you execute X → you handle errors → you serialise the result → you tell the LLM what happened → LLM continues.”

What Is an Agent?

Now we can define an agent clearly.

An agent is a client-side loop that places the LLM inside an autonomous cycle. Instead of a single question-and-answer, the agent:

  1. Evaluates the user’s goal.
  2. Determines a sequence of actions (which tools to call, in what order).
  3. Calls the harness to execute each action.
  4. Observes the results.
  5. Loops until the objective is met.

In the simplest terms: an agent is a harness wrapped in a loop. The harness handles a single tool-call cycle; the agent orchestrates many such cycles, driving toward a goal the user stated once.

The anatomy of an agent loop

A minimal agent loop in pseudocode:

def run_agent(user_goal, tools, system_prompt):
    messages = [
        {"role": "system", "content": system_prompt},
        {"role": "user",   "content": user_goal}
    ]

    while True:
        # 1. Call the LLM with the current message list + tool definitions
        response = llm.chat(messages, tools=tools)

        # 2. Did the LLM return a tool call, or a final answer?
        if response.has_tool_call():
            # 3. Harness executes the tool
            result = run_harness(response.tool_call)
            # 4. Feed the result back to the LLM
            messages.append({
                "role": "tool",
                "content": result
            })
            # Loop continues — LLM will be called again
        else:
            # 5. LLM produced a final answer — we are done
            return response.content

That is the entire skeleton. Every agent framework — LangChain, CrewAI, OpenAI Assistants, Claude Code — is a variation on this while True loop with different amounts of scaffolding around it.

What separates a toy agent from a production agent

The loop above is deceptively simple. In practice, production agents add several layers on top:

Planning. Instead of blindly calling tools one at a time, a good agent first generates a plan. It breaks the user’s goal into sub-tasks and works through them deliberately. This is not magic — the “plan” is just the LLM producing a structured list of steps in its response, which the agent then follows.

State tracking (to-do lists). As the agent works through a multi-step task, it needs to track what it has done and what remains. A common pattern: the LLM generates a to-do list at the start, updates it after each step (marking items complete, adding new ones as it discovers them), and uses it to decide what to do next. This is exactly how Claude Code operates — you can watch it generate and update a checklist as it works.

Termination conditions. The while True loop needs an exit condition. Options include: the LLM explicitly says “I am done” (returns a response with no tool call), a maximum number of iterations is reached (to prevent infinite loops), or a token/time budget is exhausted. Getting this right is critical — an agent that never terminates is a bug, not a feature.

Human-in-the-loop checkpoints. For high-stakes actions (deploying code, making a payment, deleting files), the agent should pause and ask the user for confirmation before the harness executes the tool. Claude Code does this in its plan mode — it presents what it intends to do, asks for approval, and only then proceeds to execute.

Error recovery. When a tool call fails (API timeout, permission denied, invalid input), a production agent does not just crash. The LLM reads the error message, reasons about what went wrong, and tries an alternative approach — a different tool, different arguments, or asking the user for help.

How Claude Code does it: a real-world agent in action

Claude Code is one of the most transparent examples of an agent loop in production. When you give it a task like “refactor the authentication module and add tests,” here is what happens:

  1. Plan mode. Claude Code first enters a planning phase. It reads the relevant files (using its read_file tool), understands the codebase, and generates a plan: “I will create a new AuthManager class, update the three files that depend on the old module, and write unit tests.” It presents this plan to the user and asks for confirmation before doing anything.

  2. To-do generation. Once approved, it creates a structured to-do list — not in its head, but as an explicit artefact you can see in the terminal:

  3. Execution loop. It works through the to-do list one item at a time. For each item, it may call multiple tools: read_file to understand a dependency, write_file to create the new class, run_tests to verify the change, grep to find all references to the old module. Each tool call goes through the harness — Claude Code executes the function, captures the output, and feeds it back to the LLM.

  4. To-do updates. After completing each item, it marks it done (✓) and sometimes adds new items it discovered along the way (e.g., “fix broken import in utils.py that I noticed while editing routes/login.py”).

  5. Verification. Before declaring the task complete, it runs the test suite one more time and summarises what it did. If tests fail, it loops back — reads the error, edits the code, re-runs tests — until everything passes or it asks the user for help.

This entire sequence is the agent loop: plan → generate to-do → execute step → observe result → update to-do → execute next step → … → verify → done. Every single action — reading a file, writing code, running tests — is a harness cycle. Claude Code is just a very well-engineered while loop around that harness, with planning and state tracking layered on top.

The takeaway

The most minimal agent you can think of might have just a handful of tools — read a file, search code, run a command — and loop until the task is done. Systems like OpenAI’s Codex agent, Devin, and Claude Code are elaborate instances of this same pattern, but the skeleton is always the same: LLM + tools + harness + loop = agent. What separates a toy from production is not a different architecture — it is the quality of planning, state tracking, error recovery, and human-in-the-loop checkpoints layered on top of that same loop.

Putting It All Together: A Worked Example

To make everything concrete, let us trace a single scenario end to end. We will follow one example through every concept we have covered — statelessness, multi-turn context, system prompts, client-side control, tool calls, the harness, and the agent loop.

The scenario

You have a monthly SIP of ₹15,000 that gets auto-debited on the 5th of every month. You want your assistant to answer: “How many days until my next SIP payment is due?”

The SIP due date (5th of every month) and the amount (₹15,000) are static facts. But the current date is dynamic — the LLM does not know it. So we will need a tool.

Let us walk through this in stages, labelling the component that is active at each step.

Stage 1 — The system prompt

Before any user message, you set the system message. This defines the persona and the ground rules:

[
  {
    "role": "system",
    "content": "You are a personal finance assistant for Indian users. You help track SIPs, EMIs, and bill payments. If you need dynamic information (like today's date), use the get_today_date tool. If you need to check the user's bank balance, use the check_bank_balance tool. The user has a monthly SIP of ₹15,000 auto-debited on the 5th of every month."
  }
]

Component active: System prompt. The static facts (SIP amount, due date) are baked in here. The model provider’s own system prompt sits above this and is not shown — it governs baseline safety and behaviour.

Stage 2 — The user asks a question (Turn 1)

The user sends their message. The client appends it to the message list:

[
  {"role": "system",    "content": "You are a personal finance assistant for Indian users. ..."},
  {"role": "user",      "content": "How many days until my next SIP payment is due?"}
]

This entire list is sent to the LLM API over HTTP.

Component active: Stateless HTTP + multi-turn context. The server has never seen this user before. Everything the LLM knows comes from this single JSON payload. If this were Turn 2, the list would also contain the previous assistant message — that is how context is maintained.

Stage 3 — The LLM recognises it needs a tool

The LLM reads the system prompt, sees the SIP is due on the 5th, and realises it needs today’s date to compute the difference. It does not guess or hallucinate a date. Instead, it returns a tool-call request:

[
  {
    "role": "assistant",
    "tool_calls": [
      {
        "name": "get_today_date",
        "arguments": {}
      }
    ]
  }
]

Component active: Tool call. The LLM chose a tool from the set you defined. It did not execute anything — it merely signalled, “I need to call get_today_date.” The tool definition (name, description, expected parameters) was provided by you alongside the message list when you made the API request.

Stage 4 — The harness executes the tool

The client-side code — the harness — intercepts the tool-call request. It validates the arguments (empty, which is fine since get_today_date takes none), runs the actual Python function, and captures the result:

def get_today_date():
    from datetime import date
    return date.today().isoformat()  # e.g., "2026-06-27"

The harness gets the result ("2026-06-27"), serialises it into a string, and appends it to the message list as a new message with the role tool:

[
  {"role": "system",    "content": "You are a personal finance assistant for Indian users. ..."},
  {"role": "user",      "content": "How many days until my next SIP payment is due?"},
  {"role": "assistant", "content": null, "tool_calls": [{"name": "get_today_date", "arguments": {}}]},
  {"role": "tool",      "name": "get_today_date", "content": "2026-06-27"}
]

Component active: Harness. This is your code. You validated the arguments, you executed the function, you serialised the output, and you captured any errors. The LLM had no part in this execution. The harness then sends this updated message list back to the LLM for the next step.

Stage 5 — The LLM produces the final answer (Turn 1 completes)

The LLM now sees the full picture: the SIP is due on the 5th, today is the 27th of June, so the next payment is July 5th. It computes the difference and responds:

[
  {"role": "system",    "content": "You are a personal finance assistant for Indian users. ..."},
  {"role": "user",      "content": "How many days until my next SIP payment is due?"},
  {"role": "assistant", "content": null, "tool_calls": [{"name": "get_today_date", "arguments": {}}]},
  {"role": "tool",      "name": "get_today_date", "content": "2026-06-27"},
  {"role": "assistant", "content": "Your next SIP payment of ₹15,000 is due on July 5th. That is 8 days from today."}
]

Component active: Multi-turn context. Notice how the entire history — system prompt, user question, tool-call request, tool result, and final answer — is now one growing list. If the user asks a follow-up (“Can I reschedule it?”), this entire list is resent. The server still remembers nothing on its own.

Stage 6 — What if the user follows up? (Turn 2 and client-side control)

The user asks: “Can you also check whether I have enough balance for the SIP this month?”

You, the client, decide what to include in the next request. You could:

  • Send everything — the full list above plus the new user message. The LLM sees the entire conversation and knows the SIP is ₹15,000 due on July 5th.
  • Fork — branch off from Stage 2 with a different question, ignoring the SIP conversation entirely.
  • Prune — drop the tool-call messages and only keep the system prompt + final assistant answer + new user message. The LLM would still know the answer (₹15,000 on July 5th) but would not know a tool was ever called.

Component active: Client-side control. The server never decides what context to keep. You do. You could even start a completely separate conversation with a different system prompt — the LLM has no idea these two conversations are related.

Stage 7 — What makes this an agent?

In the example above, there was one tool call, one harness execution, and one final answer. That is a harness cycle — a single loop iteration.

An agent is what happens when you wrap this in an autonomous loop. Imagine the user says: “Check if my SIP payment is due this week, and if so, check my bank balance and tell me if I have enough to cover it.”

Now the LLM must: 1. Call get_today_date → harness validates, executes, returns June 27th. 2. Reason: the 5th is next week, SIP is ₹15,000 → call check_bank_balance → harness validates, executes, returns ₹54,000. 3. Reason: ₹15,000 ≤ ₹54,000 → produce final answer: “Your SIP of ₹15,000 is due on July 5th (8 days away) and your balance is ₹54,000. You have sufficient funds.”

Each step is a harness cycle. The agent is the outer loop that keeps cycling — LLM reasons → selects tool → harness executes → feed result back → LLM reasons again — until the user’s goal is fully met.

Component active: Agent loop. The agent is not a new API feature. It is a client-side while loop around the harness: “keep going until the LLM says it is done.”

Recap: which component does what

Component What it does Who controls it
System prompt Sets persona, static facts, and ground rules You (the client)
Message list The full conversation history, resent every turn You (the client)
Tool call The LLM’s decision to use a function The LLM
Harness Executes the function and feeds the result back You (the client)
Agent loop Cycles LLM → tool → harness → LLM until the goal is met You (the client)

The LLM’s only real power is choosing which tool to call and reasoning about the results. Everything else — the context, the execution, the loop — is your code. That is what “client-side” means, and that is why the harness and the agent loop are not part of the LLM itself.

Tool Implications: Where We Go From Here

With this foundation in place — statelessness, multi-turn context, system prompts, client-side control, tool calls, harnesses, and the agent loop — a lot of the popular jargon in the AI space becomes much easier to parse. Many “advanced” concepts are just combinations of the primitives we have covered here.
